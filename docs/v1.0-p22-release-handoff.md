## 3. Security and data-protection review

- **Authorization:** protected admin operations use `AdminAPIView` and assigned capabilities; authentication endpoints inherit `AuthAPIView` and deliberately use separate pending-session/CSRF checks rather than the normal capability permission class. Publication actions additionally require domain-specific capabilities and a live admin session.
- **Two-person / independent approval:** policy-driven; the approver cannot be the plan creator in `two_person` mode, and the applier cannot be the approver. Reinstatement creates a fresh plan and does not reuse the withdrawn approval.
- **MFA:** apply, withdraw and reinstatement-apply consume a single-use step-up bound to the manifest digest and revision.
- **Idempotency:** publication apply/withdraw use unique idempotency keys and unique `(plan, event_type)` receipts; retries with the same key return the original receipt.
- **Stale revisions:** manifests bind revision digest, review ids, source digests and policy version; any drift returns 409/412 and blocks apply.
- **Rights:** text/translation scopes are applied on public readers. This session fixed Symptom descriptions embedded in Disorder detail, which previously bypassed the text scope.
- **Audit:** append-only audit events; no publication text, answers, secrets or reviewer identities in responses or audit metadata. Reinstatement adds `case.publication_reinstatement_frozen`.
- **Secrets:** no credentials, tokens or DSNs are committed. Target-environment TLS, cookie, CSRF and secret configuration is **not verified**.
- **Data protection:** canonical database untouched; tests used disposable stores; the temporary PostgreSQL cluster was stopped and deleted.

## 7. Rollback runbook

**Triggers:** public data exposure, broken authorization, failed migration, receipt/audit drift, or an operator-declared incident.

1. **Stop the bleeding without deleting evidence**
   - Disable the affected public route or worker; do not delete audit rows, receipts or plans.
   - Record the artifact SHA, migration head, time, operator and observed error codes.

2. **Application rollback**
   - Redeploy the last known-good artifact. Prefer a revert commit on a new branch; never force-push or rewrite history.
   - Keep the database at the newer schema if migrations are additive and backward compatible; verify with a disposable copy first.

3. **Migration rollback**
   - Reverse a migration **only** on a disposable copy and only if it is verified reversible with no data loss.
   - Otherwise forward-fix. Append-only audit, review and receipt tables must not be truncated to make a rollback pass.

4. **Publication rollback**
   - Withdraw the affected case publication through the MFA-guarded withdraw action; this creates a receipt and removes public visibility while preserving learner history.
   - If the withdrawal itself is wrong, use reinstatement: it requires a fresh plan, fresh approval and fresh MFA, and preserves the original `published_at`.
   - Never hand-edit `is_active`, plans or receipts in the database.

5. **Data restore**
   - Restore only from a verified backup, into a disposable environment first, and compare counts/digests and FK integrity.
   - Representative production restore and RPO/RTO are **not measured**; do not promise them.

6. **Post-incident**
   - Re-run `manage.py check`, focused publication/rights tests and the release gate.
   - Record the incident, affected receipts, root cause and follow-up in the project master and the milestone docs.
