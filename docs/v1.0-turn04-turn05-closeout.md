## W07-01 | Core/DSM duplicate candidates and archive impact

**IMPLEMENTED / VERIFIED (local engineering):** a read-only duplicate review for `category`, `disorder`, `symptom`, `concept`, `dsm-corpus` and `dsm-record`. Detection is same-kind only; `dsm-record` candidates are restricted to the same corpus; Concept aliases participate through `ConceptAlias`. Names and identities are normalized with NFKC, whitespace collapse and case folding. Tiers are explicit and ordered:

- `identity_conflict`: normalized slug/key/master_id equality (definite identity conflict, not an automatic merge decision).
- `probable_duplicate`: exact normalized `name_en`/`name_fa` equality, or alias overlap.
- `lexical_only`: token Jaccard similarity at or above `0.6`, reported as similarity only.

Every candidate carries typed evidence (`identity`, `name`, `alias` or `token`), score, active state, candidate state id and identity locator. Ordering is deterministic: tier, descending score, then primary key. The candidate pool is bounded to 400 rows and output to 50, with explicit `truncated`; `merge_available` is always `false` and `canonical_write` is always `0`. A draft without a canonical identity returns `NO_CANONICAL_IDENTITY` instead of inventing a comparison subject. No merge, delete, slug rewrite or raw archive mutation exists in the service.

The archive-impact view derives reverse relations from the live Django ORM (`ManyToOneRel`, `ManyToManyRel`, `OneToOneRel`), excludes CMS-owned tables, counts rows through the related model's base manager, and reports the declared `on_delete` class mapped to `cascade`/`protect`/`detach`/`link`/`orphan_risk`. It also exposes the current ContentState publication/review metadata, totals, and a deterministic `impact_digest`. It is a preview: `canonical_write: 0`, `raw_archive_changed: false`, and `search_graph: computed_at_read_time`; no future cascade or search-index effect is fabricated.

Both endpoints require the domain `view` and `preview` capabilities under `policy_lock`, reject any query parameter, and are not routed for unsupported kinds. The Persian RTL authoring tab is shown only for supported kinds with preview capability, and presents duplicate and impact tables with keyboard-focusable regions. The tab never appears for History or other unsupported domains, avoiding a misleading 400 path.

**Principal files:** `backend/atlas/cms_content.py`, `cms_content_views.py`, `cms_urls.py`, `tests_v100_p07_duplicates.py`; `frontend/lib/cmsDomains.ts`, `frontend/components/cms/DomainRecord.tsx`.

**Acceptance covered (9 focused tests):** identity/probable/lexical tiers without a false positive from unrelated wording, deterministic order and digest, alias overlap without auto-merge, DSM same-corpus scoping, write-free reads and draft-without-identity behavior, permission/unknown-kind/query denial, live ORM counts and `on_delete` classes, read-only impact with digest change after a new dependency, archive intent preserving canonical/dependency counts, and cross-domain denial.

## W09-01 | History ResearchRecord provenance

**IMPLEMENTED / VERIFIED (local engineering):** History detail and chronology now show the persisted `ResearchRecord.promoted_model`/`promoted_pk` locator only. Names, slugs, payloads and source ids are never used to infer a link. `promoted_model` is normalized and matched against the target model's label/name; a non-matching locator is reported as `unknown` with `PROMOTED_MODEL_MISMATCH`, never guessed into a link.

Origin statuses are explicit: `linked`, `unlinked` (`NO_PROMOTED_RESEARCH_RECORD`), `unknown`, `restricted` (`RESEARCH_SCOPE_DENIED`) and `unavailable` (`RESEARCH_VIEW_REQUIRED`). When some linked records are visible and others are cross-scope, status remains `linked` with `restricted_count`; status `restricted` is used only when all linked records are hidden. Records are ordered deterministically, capped at 10 with `truncated`, and include dataset name/version, section, external id, promoted model, latest staging decision and version. `name_en`/`name_fa` appear only with `cms_research_raw_read`.

The detail endpoint requires `cms_history_view`; lineage additionally requires `cms_research_view` and dataset scope through the existing `cms_artifacts.scoped_datasets`. Chronology uses one bulk lineage query for the page, not per-row queries. Non-History kinds return 404. The response is read-only (`canonical_write: 0`, `auto_review: false`) and contains no raw document, payload, private source text or automatic scientific approval. The RTL origin tab is gated by History domain plus capability; chronology adds an origin column that links only to authorized ResearchRecord ids.

**Principal files:** `backend/atlas/cms_provenance.py` (new), `cms_history_views.py`, `cms_urls.py`, `tests_v100_p09_provenance.py`; `frontend/app/admin-console/content/chronology/page.tsx`, `frontend/components/cms/DomainRecord.tsx`, `frontend/lib/cmsDomains.ts`.

**Acceptance covered (6 focused tests):** linked detail/chronology locator only, legacy `unlinked` and mismatched-model `unknown`, all-cross-scope `restricted` without details, partial visibility with `restricted_count`, names gated by raw-read while locator remains visible, permission/non-History/read-only contract, and no raw payload leakage.
