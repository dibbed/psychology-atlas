## W13-02: private, claim-level source provenance

A new `cms_learning_evidence` API and append-only `LearningEvidenceRevision` / `LearningEvidenceSource` models (migration `0059_w13_learning_evidence`) bind precise source locators to individual QuizQuestion explanations, Flashcard backs, DailyChallenge explanations and Distortion Practice explanations. Each revision captures actor, content SHA-256, source snapshot digest, source PK and locator. Writes require current admin session, source and learning capabilities, immutable source IDs, private/inactive/unseeded/no-history content, explicit nonempty explanation, bounds and an optimistic ETag. Source-impact scope is checked; subsequent source/content change makes the claim **requires_review**, and archived/deleted/restricted rights redact the source label/locator. UI in Persian/RTL shows status, independent refresh, focusable errors and a gated editor. Linking a source **does not** perform scientific review, authorize material rights, change canonical content, or activate/publicly publish anything. Old Quiz question evidence is not carried to a new question after replace; the append-only historical revisions remain.

### Transfer compatibility and explicit limitation

The existing `psychology-atlas-learning-authoring-v1` transfer bundle **does not carry claim-level source locators**. The new `_guard_evidence_export` rejects any export whose *current* evidence revision has source links, at initial selection and again at the worker, with `LEARNING_EVIDENCE_TRANSFER_UNSUPPORTED` (409). Thus source provenance cannot disappear silently in a seemingly complete export. Import continues to create only new private drafts with no fabricated source evidence or review approval. An explicit new empty source-link revision restores eligibility for a content-only transfer without deleting old evidence history. The Persian Transfer UI discloses this limitation and maps the error. **Full portable citation transfer is not implemented** and must use a separately designed versioned bundle and scope/rights policy before this guard can be removed.

## Daily Challenge date and timezone contract

The existing `today_challenge(date)` remains a server-local-date, dynamically eligible-pool rotation: eligible active, rights-allowed challenges ordered `(sort_order,id)`; the index is `date.toordinal() % len(pool)`. This is **not** a future editorial scheduling calendar or a guaranteed stable assignment across pool changes. The admin detail now makes the rule, active server timezone, local date, dynamic pool, and absent calendar functionality explicit. Historical attempts remain pinned to their date/challenge/choice. Synthetic tests cover timezone midnight rollover, rotation consistency and preservation of previous attempts in `tests_v100_w13_schedule.py`.
