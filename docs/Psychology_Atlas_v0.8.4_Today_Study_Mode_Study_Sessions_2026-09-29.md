# Psychology Atlas v0.8.4 — Today Study Mode + Study Sessions

Date: 2026-09-29. This record describes the implemented v0.8.4 source and local validation. GitHub PR, final-main, tag and publication outcomes are verified in their corresponding GitHub records.

## Scope and architecture

v0.8.1 owns personal StudyPlan intent, settings, availability and scope. v0.8.2 owns scheduled StudyBlock intention and its explicit completion boundary. v0.8.3 owns deterministic Recommendation V2 advice and separate append-only feedback. v0.8.4 adds one Block-anchored `StudySession` as a focus/adherence window and a read-only Today assembler. Existing SRS, Quiz, Case, Daily Challenge, distortion practice, activity and progress records retain learning-evidence authority. There is no second mastery, scoring or scheduling engine.

The backend path is `atlas/urls.py` → authenticated `study_session_views.py` or `study_today_views.py` → `study_sessions.py` or `study_today.py` → existing Plan/Block, learning, Case and Recommendation V2 queries. `/study` uses the Today response in `StudyCenter.tsx`; `/study/session/[id]` uses the Session routes and one existing canonical activity destination. Both use the frontend's existing authenticated API client and Persian/RTL page shell.

## StudySession persistence and lifecycle

`StudySession` stores its owner, Plan, nullable primary Block, immutable `block_id_at_start`, client UUID `client_event_id`, `in_progress`/`completed`/`abandoned` status, planned minutes (5–240), server start/terminal timestamps, capped `actual_seconds`, and creation/update timestamps. The primary Block is required on creation; `SET_NULL` preserves Session history if a Block is later hard deleted. Model validation checks owner/Plan/Block relationships and immutable identity. Migration `0032_v084_study_sessions.py` adds the table after 0031, lookup indexes, unique `(user, client_event_id)`, a partial unique active-Session constraint on user, and checks for duration, seconds and status/timestamp consistency. It contains no data migration or synthetic Session rows.

`POST /api/study/sessions/` accepts an owned actionable `primary_block_id`, a client UUID and optional `planned_minutes`; the active Plan and Block target are rechecked. Created starts return 201. Exact UUID replay returns the original Session with 200, including after a terminal transition; a conflicting reuse returns 409. A same-Block/same-duration request while that owner's Session is active returns that active Session, but a different UUID is not a permanent alias after it ends. A different active request returns 409. `GET /api/study/sessions/current/` and `GET /api/study/sessions/<id>/` support recovery. POST complete and abandon are idempotent for the same terminal state, and opposite terminal transitions conflict. Foreign/missing IDs receive owner-scoped generic 404 behavior.

Successful start and end writes are atomic. On PostgreSQL the service locks the owner and relevant Plan/Block rows; on SQLite the active and event uniqueness constraints remain the race guard, with bounded retries for database locks. The focused tests exercise simultaneous equivalent and different starts, complete/abandon races, replay, and database uniqueness. This local evidence does not replace a production PostgreSQL concurrency run.

The server sets `started_at` and the terminal timestamp. Terminal time is at least `started_at` if the wall clock moves backward. `actual_seconds` is floor(elapsed wall-clock seconds), clamped to 0–86,400. Active responses calculate `elapsed_seconds` as of their server `as_of`; `elapsed_capped` indicates a raw interval beyond 24 hours. A browser timer is display only. These values are neither verified attention nor a source of capacity, Block completion, progress or mastery.

## Today API, time and capacity

`GET /api/study/today/` is authenticated, owner-scoped, rejects unexpected query parameters, and performs no writes. The `v1` response contains `as_of`, study `local_date`/timezone, capacity, current Session, SRS review counts, active Plans, today/overdue Blocks, Daily Challenge state, Next Action and nested Recommendation V2. Each Plan and Block list reports an exact total and a maximum 20-item display slice with `truncated`. Recommendations retain their established default eight-item limit. The populated query regression measured **31 queries against a 40-query ceiling** with 24 active Plans, 31 today Blocks, 43 overdue Blocks, 85 due cards, 13 Sessions, 12 QuizAttempts, 12 CaseAttempts and dismissed feedback; displayed lists stayed bounded while totals remained exact.

The user's valid IANA study timezone defines the local Plan/Block day and SRS overdue midnight. Missing or invalid settings fall back to application timezone without creating settings on a GET. SRS due instants remain canonical. Daily Challenge keeps its existing application-timezone day and attempt semantics, shown separately as `challenge_date`; v0.8.4 does not migrate historical Challenge dates.

Capacity is measured in minutes: `available = min(user default daily minutes, sum(active Plan availability for local weekday))`; `scheduled = sum(today active-Plan Block estimates with pending, in-progress or completed status)`; `completed = sum(today completed Block estimates)`; `remaining = max(available - completed, 0)`; `over_capacity = max(scheduled - available, 0)`. These are planning/adherence totals, not Session elapsed time or learning outcomes. Overbooking is reported rather than hidden.

## Deterministic Next Action

The selector takes the first applicable branch in this order: current Session (resume even if its old Block action is unavailable); resumable owned Case attempt; actionable overdue Block; actionable today Block; due SRS review; available and incomplete Daily Challenge with remaining and unscheduled capacity; the first visible non-dismissed Recommendation V2 item; deterministic onboarding. A Case attempt pinned to a retired revision remains resumable when its current step is valid and the Case has a current published runnable revision, matching the canonical Case route. Block ordering is scope priority descending, date, sequence, Plan ID and Block ID. Onboarding chooses create/review Plans, the lowest-ID active missing or stale schedule, new SRS, or review Plans as applicable. A stale schedule warning does not discard a preserved actionable Block. The response includes a reason code and canonical action route, not a new score or clinical recommendation.

Today reuses `assemble_recommendations()` and the released V2 candidate/feedback policy; it does not fork ranking, suppression or feedback writes. Session or Block action navigation goes to existing flashcard, Quiz, Case, distortion, content, notes or Challenge routes. When a target becomes inactive after a read, start and canonical activity paths check eligibility again.

## Canonical evidence boundary and frontend

Starting, completing or abandoning a Session never calls Block completion, changes SRS due dates, scores a Quiz/Case, submits a Daily Challenge or writes practice/progress evidence. The focused page exposes Block completion as a separate explicit action through the existing endpoint. Quiz, revision-bound Case, flashcard and distortion Blocks still require their existing owner/target-matched records; reading/review confirmation records adherence only. Session start does not advance the Block evidence floor. Phase 6 browser QA observed a completed Session leaving its Block pending, evidence-required completion failing before canonical activity and succeeding after the original learning flow recorded it.

The Today Command Center at `/study` shows the next action, Session resume, study-local date, capacity and overage, due/new cards, active Plans and stale schedule, today/overdue Blocks, V2 recommendations, Daily Challenge and existing study context. The focused `/study/session/[id]` page shows server timing, planned duration, Block status, one canonical action, explicit Block completion, Session complete/abandon, and safe navigation if the Block is unavailable. Anonymous visitors get a login path; private Today and Session data never render without authentication. The browser retains the start UUID for retry/recovery and refreshes current state after navigation or feedback.

## Security, closure and deferred scope

Session/Today reads and writes start from the authenticated owner. Start accepts no client owner, Plan, score, action URL, elapsed seconds or completion claim. Cross-owner Session and Block access fails without revealing ownership. HTTP start payloads are bounded and validated; canonical target eligibility is rechecked on writes. Partial uniqueness and owner/event identity are enforced in SQLite and migration state.
