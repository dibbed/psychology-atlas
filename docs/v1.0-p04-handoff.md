## State machine and scientific semantics

`ScientificReviewStatus` remains exactly `unreviewed / source_checked / reviewed`. These are derived review facts about the current proposal; Category and Disorder do not acquire a fabricated canonical review field. Editorial revision status, scientific review and canonical publication remain separate.

| From | Command / result | Required conditions |
| --- | --- | --- |
| draft | submit → submitted | `cms_core_submit`, full typed payload validation, current canonical base, evidence for all populated fields, locked source existence and frozen hashes |
| submitted | assign → in_review | Reviewer has core view/entry and the exact review-type capability; policy conflicts checked |
| in_review | reassign → in_review | Task still queued/assigned, current content and task versions; assignment history retained |
| in_review | source approve → in_review / source_checked | Assigned source reviewer, complete resolved explicit evidence, exact subject/dependencies/policy; separate decision |
| in_review | scientific approve → approved / reviewed | Assigned scientific reviewer, fresh explicit source approval and exact scientific proposal binding |
| in_review | reject → changes_requested | Closed rejection reason plus at least one allowed field; other task cancelled |
| changes_requested | save → new draft → submit | Existing proposal service creates a new immutable draft and new tasks; old decisions cannot approve it |
| submitted / in_review | reopen → draft | Core edit + submit, exact current version; tasks cancelled and history retained |
| approved | reopen → superseded → draft | Two append-only editorial snapshots; invalidation and reopen audited; earlier approvals retained |
| legacy / discarded / terminal task | decision/submit rejected | No automatic legacy review or terminal badge mutation |

No PATCH of `review_status` or generic task badge writer replaces these commands. Existing `ContentRevision` rows are immutable; every lifecycle transition appends a new snapshot and advances the anchor CAS. Successful review and audit share one commit. Failed/denied API audit uses the existing independent post-rollback channel.

## Exact decision binding, assignment and policy

A decision binds the immutable draft subject ID, schema, payload and canonical base hash, with a separate dependency digest. Dependencies include explicit source provenance fields, locator/field mapping, canonical Category context for existing Disorder, and all current DisorderSource membership/source IDs/notes and linked source provenance. Creation/update timestamps alone are excluded. Canonical drift is blocked for reconciliation rather than overwritten.

Freshness checks live dependencies, exact payload, current policy, reviewer availability/current capabilities and a matching append-only approval decision. Mutable task status alone cannot authorize approval. Source disappearance is explicit `EVIDENCE_MISSING`; a source deleted between the initial count and locked snapshot cannot be silently omitted. Source approval requires the exact requested source-ID set and the existing shared resolved-source contract.

Solo-owner permits an author to review only when that reviewer is an effective owner; source and scientific decisions separately require `self_review_ack: true` and retain that fact. Two-person excludes every prior draft contributor of that proposal, including owner/superuser. Assigning another person then deciding as the author is rejected. Assignment and decision authority are scoped to `cms_review_decide_core_source` or `cms_review_decide_core_scientific`.

The core policy page requires effective owner plus the separate `cms_settings_edit` capability, strong policy ETag, a closed reason and single-use MFA proof bound to `review_policy`, target `1`, and the exact `{mode, reason}`. Policy history stores before/after modes; audit identifies action, field, reason and old/new versions. Every actual policy change increments its own version. Toggling two-person back to solo-owner never revives earlier approvals or partial checks: reopen and a new submission are required.

The global role-policy lock precedes session/permission checks, target locks and content/task version checks. PostgreSQL source snapshots reuse the existing Brain curation lock and row locks; SQLite uses its configured IMMEDIATE transaction. Same-version concurrent decisions have exactly one commit. Revocation waiting on the shared role boundary is rechecked before decision.

## API and UI

All routes below are under `/api/admin/`; protected requests use the existing MFA CMS session, CSRF, server permissions, `Cache-Control: no-store` and request IDs.

| Route | Contract |
| --- | --- |
| GET `reviews/` | Paged core anchors; allowlisted `kind`, `status`, `q`, `mine`, `page`, `page_size`. Includes real draft/legacy/stale state, not fabricated approvals |
| GET `reviews/{kind}/{id}/` | Current proposal, strong ETag, independent scientific status, fresh-approval blockers, policy, tasks/evidence and actual canonical eligibility |
| POST `reviews/{kind}/{id}/submit/` | `{evidence: [{source_id, locator, fields}]}`; content `If-Match`; one to twenty bounded witnesses |
| POST `reviews/{kind}/{id}/assign/` | `{task_id, task_version, reviewer_id}`; content `If-Match` |
| POST `reviews/{kind}/{id}/decide/` | `{task_id, task_version, outcome, reason, fields, self_review_ack}`; source/scientific authority and assigned actor enforced |
| POST `reviews/{kind}/{id}/reopen/` | `{}` with content `If-Match`; explicit new review lifecycle |
| GET `reviews/{kind}/{id}/history/` | Paged immutable decision/assignment/invalidation history with hashes, evidence, policy and retained pseudonymous attribution |
| GET `reviews/{kind}/{id}/reviewers/` | Paged candidates for an exact `review_type`; conflicts are explicit and blocked in service |
| GET `reviews/sources/` | Paged bounded title/DOI/PMID lookup; no raw source metadata or protected payload |
| GET/POST `reviews/policy/` | Core mode/version and paged history; audited bound-step-up mutation |

UI routes are `/admin-console/reviews`, `/reviews/{kind}/{state_uuid}` and `/reviews/policy`. Existing Category detail and dashboard/navigation reach the queue. The specialized Disorder editor, other domain adapters, rights/terminology reviews and publication retain their later milestone ownership. Review approval is not canonical publication or a completed publication selection.

Loading, empty/error, field validation, forbidden scope, stale preconditions, pending source check, reviewer conflict and uncertain write outcomes have separate UI states. A lost/unreadable/5xx mutation or failed follow-up reload locks new writes until an explicit successful server reload; it never automatically repeats the command. Forms use the existing in-memory dirty/leave protection, current-account recheck and session invalidation. No credentials or snapshots enter localStorage. Source identity, scientific names and hashes use LTR/bidi handling inside RTL layouts.

## Real journey and invalidation evidence

The fixture is explicitly synthetic, not scientific content. The browser created a new Category proposal in the existing editor, supplied a source plus section/table locator and supported fields, then completed the actual UI workflow:

`draft v1 → submitted v2 → source assignment v3 → scientific assignment v4 → source_checked v5 → approved/reviewed v6`

Both approval decisions share the exact immutable subject/revision and dependency hashes and separately record explicit owner self-review. No canonical Category row is created for the draft. A real fixture source DOI mutation then leaves the editorial history intact at v6 but returns `eligible=false`, `scientific_status=unreviewed`, `DEPENDENCY_CHANGED`. Explicit reopen appends superseded v7 and draft v8. The UI changes policy using MFA and audit, submits the new subject, blocks the owner's self-assignment in UI and service, and completes source/scientific approval using an independent reviewer. Deleting the explicit source afterwards yields `EVIDENCE_MISSING` and prevents eligible approval, with the Persian blocker visible in UI. All earlier decisions remain in history.

Source mutation/deletion in this journey is a guarded synthetic fixture injection because P05 owns the source editor. Submission, assignment, decisions, policy change and reopen are real UI/service operations. Screenshots include approved desktop, source-invalidated desktop, invalidated 320px detail and independent two-person approval. No unexplained browser runtime/console error occurred.
