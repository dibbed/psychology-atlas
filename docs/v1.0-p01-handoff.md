## API contract

- `GET auth/csrf/`; `POST auth/login/` with username/password; `POST auth/verify/` with token and method `totp` or `recovery`; `POST auth/logout/`; `GET me/`, `GET catalog/`, all under `/api/admin/`.
- Password authentication is a five-minute pending session, not a CMS session. Maintained enrollment at `/account/two_factor/setup/` or package login at `/account/login/` requires `POST /api/admin/auth/complete/` within 60 seconds of OTP verification. Enrollment proof is consumed by django-otp's replay guard. Raw Django admin sessions and owner JWTs cannot authorize Admin APIs.
- `POST auth/step-up/` binds `action`, `target_id` and exact `payload` for ten minutes, rotates the session and authorizes one sensitive mutation. Targets are integer IDs except `revoke_session`, which binds the exact session UUID. Actions: `user`, `group`, `create_group` (target 0), `delete_group`, `revoke_account`, `revoke_session`, `revoke_mfa`, `regenerate_recovery`.
- Role lookup/grants: `GET roles/permissions/`, `GET/POST roles/groups/`, `GET/POST roles/groups/{id}/`, `POST roles/groups/{id}/delete/`, `GET/POST roles/users/{id}/`. User mutation accepts CMS permissions/groups and active/staff/superuser flags only. Unrelated direct permissions survive. Foreign-permission groups cannot be granted through CMS. Mutations require the global role-policy ETag in `If-Match`; missing = 428, stale = 412. The PostgreSQL advisory lock or SQLite IMMEDIATE transaction serializes permission, membership and status changes; CAS and last-owner checks run inside it.
- `GET sessions/` lists self by default; explicit `user_id` requires `cms_user_revoke_sessions`. Session IDs are opaque; raw Django session keys are never returned. `POST sessions/{uuid}/revoke/` can revoke self-owned sessions; other users require capability and bound step-up. `POST users/{id}/revoke-sessions/` requires capability, bound step-up and `If-Match`, revoking CMS sessions and both JWT generations. Session-list clients obtain the role-policy ETag from a role lookup before mutations.
- Groups/sessions use 30 rows by default, maximum 100, and allowlisted query parameters. Every protected API rechecks current DB permissions. Missing/expired CMS sessions = JSON 403 `UNAUTHENTICATED`; denied capability = 403 `PERMISSION_DENIED`; anonymous login/action CSRF failures = 403 `CSRF_FAILED`. Private responses use `Cache-Control: no-store`.

Idle lifetime is 30 minutes, absolute lifetime eight hours. Cookies are host-only `admin_sessionid` (HttpOnly, SameSite=Lax, Path=/) and separate `admin_csrftoken`; Secure defaults on outside DEBUG. No admin token is stored in localStorage. Auth User/Group forms are read-only; raw Permission/OTP/session/security/JWT-token admin writers are unregistered.

## MFA and recovery

Integration pins `django-two-factor-auth==1.18.1` and `django-otp==1.7.3`, exercised on Django 5.2.17, DRF 3.18.0 and SimpleJWT 5.5.1. Setup/login follow the [official integration](https://django-two-factor-auth.readthedocs.io/en/stable/implementing.html). The [published password-storage advisory](https://github.com/jazzband/django-two-factor-auth/security/advisories/GHSA-vhr6-pvjm-9qwf) affects <=1.11; installed new packages and their resolved dependencies had no matching OSV advisories on this date. This is a dependency lookup, not a comprehensive security certification.

At `/account/two_factor/backup/tokens/`, GET shows only the remaining count. Generating ten replacement codes requires bound `regenerate_recovery` step-up and CSRF; only the successful POST displays them, once. Existing codes are never redisplayed. Package algorithms, device locks, throttling and one-time static-token consumption are reused. `POST /api/admin/auth/mfa/revoke/` requires self-bound step-up and `If-Match`, deletes devices and revokes sessions/JWTs; the package's unguarded disable route is blocked.

Offline owner recovery requires trusted host access and independent identity verification. Record the authorization/ticket outside the application, stop any active enrollment, then run `python manage.py cms_recover_owner --user-id <owner> --reason <ticket-reference> --identity-verified`. The command only accepts an active staff owner, atomically removes MFA and revokes tokens/sessions, and records a minimal security outcome. It preserves ownership and the password; reauthenticate with that password and reenroll, then generate/store replacement codes and verify session/JWT denial. The flag is operator attestation, not an identity provider. Free-text reasons and credentials are not copied into security events. Email/SMS recovery is `UNAVAILABLE`.
